## The method table is useless; the order is everything

Most tutorials answer missing data with a table of methods: forward fill, linear interpolation, mean, KNN, model-based. The table is nearly useless because it skips the only step that matters — **establishing what the gap is**.

@fig t5-gaps

Industrial data holds at least four things that look like gaps, and they demand opposite treatments.

| Class | What physically happened | What the record shows | Correct action |
|---|---|---|---|
| Comms dropout | The process was running | The data was lost | Interpolate — the curve is smooth there |
| Planned shutdown | The machine really stopped | The record is right: standby | **Keep it and flag it** |
| Instrument fault | The process was running | Values present, and all wrong | Mark bad, do not trust |
| Genuine zero | The machine was off | The record is right | Do nothing |

Treating all four with one method is the most common systematic error in industrial time-series projects.

## Why smoothing a shutdown is the most expensive mistake

Linear interpolation turns an eight-hour shutdown into a ramp and the data looks clean. What you have actually done is:

1. tell the model that no shutdown happened — precisely the pattern you needed it to learn; and
2. **destroy your only examples of one**.

The second is the fatal part. Maintenance is scheduled in advance, and next month's shutdown is already on the calendar. But knowing *when* one is coming only helps if your history still shows what one *looks like*. Interpolate them all away and the level the model learns for "shutdown day" is a normal day, and the calendar entry buys you nothing.

Switch the bench's defect to a planned shutdown and linear interpolation drops to last place — 17.4% against a best of 14.3%.

## But interpolation is not always wrong

Switch to spike outliers and linear interpolation moves to the front. The reason is direct: an isolated bad point has true values either side, the process was running steadily, and the interpolant is nearly the truth — while falling back to the same slot a day earlier imports a whole day of difference for nothing.

That is this chapter's argument, and the point of the table: **no single filling method is right for every defect**. On the bench, classify-then-treat is consistently first when all four defects are mixed, while every single method comes last on one class or another.

## Flagging is safer than filling

Even with the class identified correctly, prefer flagging to filling. Give the model an `is_bad` or `is_shutdown` boolean and let it learn what to do with that stretch.

Two reasons:

- trees **support missing values natively**, giving missingness its own branch at a split, which is more honest than inventing data;
- filling injects **confident fiction** while a gap injects only missing information. The model learns your invented segment as a real pattern, and can never learn that there was no data here.

## Outliers: error, or event?

One last thing. Rules like three sigma kill genuine spikes in data with regime changes — a real machine inrush is statistically an outlier.

Before deleting an outlier, ask: **is it an error, or an event?**

The evidence is not statistical but correlational. Did other tags move at the same instant? Is there a matching entry in the shutdown log? What does the work-order system say happened that day? An isolated spike with no reaction from any other tag is probably an instrument fault; a spike accompanied by rising current and temperature is a real start-up.

## Exercises

1. Classify every suspect point in your own data into the four classes. Can you? If not, what information is missing?
2. List every planned shutdown in the last six months and count how many survive in your training set uncleaned. Fewer than six and the model cannot learn what a shutdown looks like.
3. Step through all five defect types on the bench and record which treatment wins for each. That table is your own cleaning rulebook.
4. Add `is_bad` and `is_shutdown` columns to your feature table, retrain, and measure the change.
