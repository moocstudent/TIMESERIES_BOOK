## The workhorse of this field

On tabularised series with strong calendar structure and moderate data, gradient-boosted trees remain the steadiest choice. The front of the famous ASHRAE building-energy competition was uniformly LightGBM ensembles — not for lack of deep-learning skill, but because at this data size and structure trees really are more accurate, faster and less fussy.

## The mechanism: fitting residuals one tree at a time

Boosting does not fit one strong model. Each new tree fits the residual left by all the previous ones.

1. Start with a constant prediction, the training mean;
2. Compute the residual and fit a shallow tree to it;
3. Add that tree's output, scaled by the learning rate, to the prediction;
4. Return to step 2.

The learning rate controls each tree's contribution; depth and leaf count control a single tree's expressiveness. Add trees one at a time on the bench and you watch training error fall monotonically while validation error turns upward past some point — that divergence is where early stopping belongs.

## The parameters that actually matter here

| Parameter | What it does | Industrial-series range |
|---|---|---|
| learning_rate | Step size per tree | 0.03–0.05, paired with many estimators |
| num_leaves | Single-tree expressiveness | 31–127; LightGBM grows leaf-wise, which overfits faster than depth suggests |
| min_child_samples | Minimum rows in a leaf | 20–60 on 100k rows; the main guard against overfitting |
| feature_fraction | Features per tree | 0.7–0.9 |
| objective | Loss | l1 is steadier against residual spikes, l2 more sensitive to large errors |

Those are the ones worth tuning carefully. The rest rarely change the answer on this task.

## A discipline that may not be broken

**The early-stopping validation set must be the later window in time.**

Using a randomly carved validation set for early stopping is DT4's leakage committed in a new place. The bench quantifies the consequence: a random validation set reports 5.3% while the model's true test error is 6.5% — optimistic by 1.2 points.

Interestingly, as a signal for *where* to stop it is not bad: it picks tree 26 against an optimum at 21, worth 0.09 points. What it lies about is the **absolute level of the error** — the number that goes into your report and your contract.

A later-in-time validation window is far more honest, with a bias of about 0.2 points, but it covers one short stretch with few samples and is a jumpy stopping signal. The two failures differ in kind: a random split lies about the level, a time split loses precision about where to stop. The answer is not to choose between them but EV1's rolling-origin backtest, whose multi-fold mean is both unbiased and steadier.

## Two traps

**Feature importance.** The default split-count plot misleads, because high-cardinality features split often by construction. Read gain instead, or more reliably use permutation importance — shuffle one column within the evaluation window and measure how much worse it gets. The shuffle must stay inside that window; shuffling across the whole dataset mixes regimes and overstates every feature.

**Categorical features.** One-hot encoding an equipment id or product code explodes at high cardinality and gains nothing. LightGBM's native categorical support is usually enough; target encoding is stronger but must be computed **inside the fold** or it is leakage again.

## Exercises

1. Halve the learning rate and double the tree count on your data. What happens to final accuracy and to variance?
2. Switch the early-stopping validation set from random to later-in-time and record both numbers: what validation reports, and the final test score.
3. Re-rank your features by permutation importance and compare with the default split plot. Which feature moved most?
4. Replace a one-hot encoded high-cardinality categorical with native categorical support and measure training time and accuracy.
