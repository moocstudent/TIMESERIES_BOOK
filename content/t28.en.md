## Connecting the model to the plant, and the thing most underestimated

## The interface's reliability requirement exceeds the model's

A forecast creates value only once written back to the plant system — EMS, SCADA, MES, an energy platform — and that interface's reliability requirement is usually higher than the model's.

Four things to get right:

**Protocol**: OPC UA, Modbus, REST, a database table, a file drop. You do not choose this; the site already has one.

**Idempotency and retry**: a repeated write must never create two forecasts. Derive an idempotency key from the content — a hash of date, tag and model version — and have the server return 409 on a repeat, where **409 is success, not an error**.

**Clock synchronisation**: your timestamps must match the site's, or a correct forecast lands on the wrong instant.

**Version compatibility**: the contract must survive a model upgrade.

One more that gets forgotten: **validate before writing**. Ninety-six slots, no NaN, within this plant's physical range. The EMS will act on this number, and a NaN reaching a control loop is worse than no write at all.

## Alerting is an ROC problem

@fig t28-roc

Loose thresholds produce false alarms and the operators start ignoring them within a fortnight; tight ones produce misses and the model is effectively absent when it matters.

Most people start by trying three sigma and seeing what happens. This chapter argues for the reverse.

1. Ask the operators **how many alerts they will read properly in a shift** — two to five, empirically;
2. derive the permitted false-alarm rate from that number;
3. read the threshold off the ROC curve.

On the bench, three alerts a shift implies 1.2σ and catches 100% of real anomalies, while copying three sigma catches only 67% with fewer false alarms. On this data, three sigma gives away a third of the real events for nothing.

The point of the ordering is that **the binding constraint is human, not statistical**.

## Alert fatigue is a quantity you manage with numbers

Not an attitude problem. The concrete device is **tiering**.

| Tier | Threshold | Where it goes |
|---|---|---|
| Notice | 1.2σ | Dashboard |
| Warning | 2.0σ | Dashboard plus daily digest |
| Act now | 3.2σ | Pushed to a person |

Only the top tier reaches a person; the rest stay on a dashboard. It is the only way to hold fatigue down without sacrificing detection.

## Trust is built on three concrete things

Operators do not trust a black box. Trust is not built by persuasion but by three things you can write as code.

**Explainable**: every forecast carries its main drivers — "high today because it is 34 degrees and line B is at full rate". SHAP values or tree feature contributions are enough; you do not need elaborate interpretability machinery.

**Comparable**: the screen always shows the model, the naive baseline and the actual together, so people see the value for themselves rather than being told about it.

**Traceable**: when something goes wrong, every input to that forecast can be retrieved — which requires that you started archiving on OP1's day one.

## One last recommendation

For the first month, let the model **advise** rather than control, and let people see enough of its mistakes.

A model that takes control before trust has formed gets switched off the first time it is wrong, however good its average was. A model watched in advisory mode for a month is treated, when it errs, as "wrong this time" rather than "unusable".

## Exercises

1. Test your write-back interface: submit the same forecast twice. How many appear?
2. Ask the control room once how many alerts they will read per shift, and derive your threshold from that number.
3. Attach the top three drivers to every forecast, show operators for a week, and listen to what they say.
4. Add the baseline to the dashboard beside the model. Does anyone notice?
