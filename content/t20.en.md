## The most useful of the free tiers

Kaggle gives every phone-verified account thirty GPU hours a week (T4×2 or P100) plus a complete dataset, notebook and versioning system, with no payment details required. This chapter treats it as a production environment.

## Three hard limits

Together they shape how you work.

| Limit | Value | Consequence |
|---|---|---|
| GPU session | 9 hours | Reclaimed beyond it — a structural problem, not a quota one |
| Weekly GPU quota | 30 hours | Resets periodically; long jobs spread across weeks |
| Output directory | /kaggle/working, 20 GB | **Only this survives**; everything else is gone |

CPU sessions run to twelve hours with a much looser quota. So if your job does not actually need a GPU — PF1 already measured that — a CPU session is the freer choice.

## Data: a private dataset

Package your history as a **private dataset** through the web UI or `kaggle datasets create` / `version`, and it mounts read-only at `/kaggle/input/<slug>/` for the notebook to read.

Datasets are versioned, and that fact is the foundation of the technique below.

## The correct way to run: submit in the background

**Do not sit watching it in a browser.** An interactive session is reclaimed when idle and holds your quota meanwhile — every minute you watch is billed.

Write the notebook, submit it with **Save Version → Save & Run All (Commit)**, close the browser, and come back for the results. From a shell that is `kaggle kernels push`, with a `kernel-metadata.json` that puts the GPU switch, the internet switch and the input datasets into version control.

Kaggle also schedules notebooks, which is enough to stand up a first version of a daily automatic retrain.

## The core technique: resuming across sessions

This is the chapter's key, and where every earlier mention of checkpoints lands.

The cycle:

1. the training loop writes checkpoints into `/kaggle/working/ckpt/`;
2. when the session ends, `kaggle datasets version -p ckpt -m "segment 1"` publishes it as a **new dataset version**;
3. add that dataset to the next notebook's input sources;
4. on start-up the next session finds the checkpoint under `/kaggle/input/`, loads it and continues.

The bench makes it computable: a 26-hour run with checkpointing (6% overhead) needs four sessions across one week, while **with checkpointing off it never finishes** — not slower, but with each reclaimed session returning progress to zero and you starting again.

One detail is worth building in: the loop should **stop cleanly before the wall**. A checkpoint written at eight hours thirty is worth far more than an epoch killed at nine hours with nothing saved.

## A compliance question to ask first

Plant history is usually the customer's asset, and some of it falls under sector-specific data rules. Uploading it to an overseas platform is an action requiring **written clearance** in many projects, not a technical footnote.

Three workable compromises:

- upload only **rescaled and de-identified** curves, stripping absolute magnitude and identifiable time anchors;
- use **synthetic data** for architecture selection and move the final training back inside the network;
- choose a platform that keeps the data in country (listed in the next chapter).

Settle this on day one of the project, not in the final week.

## Exercises

1. Upload a de-identified dataset as a private dataset and read it from a notebook.
2. Write a training script that checkpoints, run it, publish the checkpoint as a dataset version, then start a new session and resume.
3. Use the bench to compute how many sessions and how many weeks your own job needs.
4. Put `kernel-metadata.json` into your repository and try one `kaggle kernels push`.
