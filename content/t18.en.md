## Treat the training loop as an engineering object

This chapter is not about designing networks but about making training controllable — and it produces exactly the numbers the next module needs.

## The four memory terms

This is the only basis for deciding what card you need.

| Term | Size | Note |
|---|---|---|
| Weights | parameters × bytes per parameter | 2 bytes each in bf16 |
| Gradients | same size as the weights | only the trainable part under LoRA |
| Optimiser state | parameters × 8 bytes for Adam | two fp32 moments |
| Activations | ∝ batch × sequence length × hidden width × layers | **usually the largest** |

@fig t18-vram

A 200M-parameter model in bf16 occupies 0.4 GB of weights and needs 9.6 GB to train — twenty-four times as much. The extra 7.2 GB is activations.

That is why **batch size and sequence length are the two effective memory knobs**: they touch only the last term, and the last term is usually the largest. Changing the architecture moves far less.

Two ways to cut memory:

- **LoRA**: about one percent of the weights trainable, so gradients and optimiser state nearly vanish and the model fits a free T4;
- **Gradient checkpointing**: do not store intermediate activations, recompute them on the backward pass, cutting activations to about a fifth at a cost of 20–30% speed.

Inference needs only 0.5 GB, having no gradients and no optimiser state. That is why training rents a card while inference runs on the plant's old server.

## Batch, learning rate, warmup

Doubling the batch usually calls for multiplying the learning rate by between √2 and 2, or convergence slows. Warmup and cosine decay are effectively standard alongside:

- **warmup**: rise linearly to the target rate over the first few hundred steps, so the weights are not scrambled immediately;
- **cosine decay**: fall toward zero late in training so the model settles into a minimum.

## Early stopping: the same discipline

On a series, the early-stopping validation window must be the later segment — ML2's rule applies here too.

How much patience depends on how jumpy your validation curve is, and **jumpiness usually means the validation set is too small**. If you find you need patience above ten for stability, go and check the window length first.

## Checkpointing: optional locally, mandatory on a platform

This is the skill the rest of the book leans on. Every epoch, save:

- model weights
- optimiser state (Adam's moments; without them you are re-warming up)
- the current epoch number
- RNG state, if you need strict reproducibility

Write **atomically**: write a temporary file and rename. A half-written checkpoint is worse than none, because you discover it only when you try to resume.

Locally this is insurance against a power cut. On a platform with a nine-hour session wall it is the difference between a run that finishes and one that never does — which the next chapter computes exactly.

## Reproducibility: five things

Pin the seeds for Python, NumPy and the framework, enable deterministic kernels where it matters (at some cost in speed), and write the seed into the experiment log.

Without it you cannot tell whether the difference between two runs came from your change or from luck. And on deep models, the spread between seeds is frequently larger than the improvement you worked hard to obtain.

## Exercises

1. Estimate your model's memory with this chapter's calculator and compare it with `nvidia-smi`. How far apart?
2. Halve the batch, then halve the sequence length, and measure the memory saved by each. Which is more effective?
3. Write a training loop that survives Ctrl-C and resumes. Test it for real.
4. Train the same configuration with five seeds and record the standard deviation of the validation error. Every later comparison needs that number.
